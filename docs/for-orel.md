# ל-Claude של אוראל: איך בונים את המשחק עכשיו

נכתב ב-30.10.2026 על ידי ה-Claude של ניר, אחרי יום שבו נבנו כ-25 PR במקביל. הקובץ הזה לא מחליף את [CLAUDE.md](../CLAUDE.md), ש-Claude קורא לבד. הוא מסביר את מה שלמדנו בדרך, כדי שתוכל לעזור לאוראל באותה מהירות.

## מה מחכה לאוראל (להציג לו קודם)

1. **הבעלות על הזירה והקרב.** ניר הציע שאוראל יהיה אחראי על הפרק "זירה וקרב" ב-[roadmap.md](../roadmap.md): נשק לכל דמות, חפצים מסתובבים, סקילים, קומבו בין סוגי נזק, עוד זירות, עוד אויבים ובוסים. כל הרעיונות של אוראל עד היום היו רגעי קרב, אז זה מתאים לו. צריך ממנו כן או לא.
2. **ההחלטות של היום.** במסמך הרעיונות, הפרק "החלטות של ניר" והפרקים אחריו: מסך לרוחב, קרב גמיש, כלכלה עם 36 משאבים, מסחר ביניהם, וקווסטים. כולן מסומנות "מחכה לאוראל". הכי חשוב לשאול עליה: המשחק עבר למסך לרוחב.
3. **כניסה עם Google ב-Supabase.** הפרויקט `fun-house` כבר פתוח (#30). חסר רק מפתח כניסה מ-Google Cloud, שמדביקים ב-Supabase תחת Authentication ← Providers ← Google. עזור לו בזה צעד-צעד, ואל תדפיס סודות ואל תשמור אותם בקבצים. לקוד צריך רק את הכתובת ואת המפתח הציבורי (anon).
4. **דמות משלו.** ניר יצר את הגיבור שלו ב-Gem של ג׳מיני, והוא כבר במשחק בתלת-ממד (`?hero=pilot`). אוראל יכול לעשות אותו דבר עם הנווד שלו. איך עושים: [docs/3d-assets.md](3d-assets.md), בפרק "מבצע ג׳מיני", והכלים ב-[tools/pilot3d](../tools/pilot3d/README.md). בחינם, וכחצי שעה.
5. **איך הוא רוצה לעבוד:** האם ה-Claude שלו ממזג לבד כשהבדיקות ירוקות (כמו אצל ניר), או מחכה לאישור שלו. ראו "מיזוג" למטה.

## איך עובדים בלי להתנגש

- **[roadmap.md](../roadmap.md) הוא התוכנית.** "תמשיך" פירושו: לקחת את המשימה הפנויה הבאה מהחלק שלך. כשמתחילים, מסמנים 🔨. אוראל לוקח רק מ"זירה וקרב", ומשימה שלו שמחכה שבוע עוברת לניר.
- **ענף לכל משימה, מ-main מעודכן.** קודם `git fetch` ואחר כך `git merge origin/main`. ב-worktree, ה-main המקומי בדרך כלל ישן.
- **כשמישהו אחר מיזג, מסנכרנים:** `git merge origin/main`, ובהתנגשות שומרים את שני הצדדים. כמעט תמיד שני השינויים נכונים.
- **`js/models3d.js` לא ממזגים ביד.** לוקחים את הגרסה של main, ואם הענף שינה את `tools/build3d.js`, מריצים אותו מחדש.
- **לא כותבים שורה ביומן מכל ענף.** כל הענפים כותבים לשורה הראשונה, ואז כל מיזוג מתנגש בכולם. סשן יחיד כותב שורה בסוף, ובעבודה מקבילית כותבים שורת סיכום אחת.
- **מקום גדול נפתח בלחיצה, לא במעבר.** ניר נכנס בטעות לזירה כשעבר ליד השער. אותו כלל לשערי העולם ולשיחה עם NPC.

## בדיקות

- **בתלת-ממד לא בודקים במחשב.** במחשב בלי כרטיס גרפי בדיקה בתלת-ממד לוקחת כ-15 דקות ומאטה את כל המחשב (קרה לניר). במחשב: לכל היותר `node tools/check.js --gfx 2d` אחת. את שלוש הבדיקות (תלת-ממד, דו-ממד, אנגלית) GitHub מריץ על כל PR.
- **בדיקה אדומה ב-GitHub:** `gh pr checks <n>` מראה מה נכשל, ו-`gh api repos/orel600/fun-house/actions/jobs/<job-id>/logs | grep ✗` מראה את השורה. הרבה פעמים מה שנכשל הוא הבוט, לא המשחק: הוא לוחץ על כפתור ששמו השתנה, או סופר מספר שזז כשמערכת אחרת נכנסה.
- **מכניקה חדשה = שלב בבוט.** `botStep` ב-`tools/check.js` מגיע אליה, והדוח בודק שהיא מופיעה, עובדת ונגמרת.

## מיזוג ופרסום

- **כל PR מקבל קישור לטלפון** בתגובה של הבוט (Vercel). הקישור הקבוע של main: https://fun-house-zeta.vercel.app. התגובה של הבוט עם הקישור היא לא בקשה לשינוי, אין מה לתקן בה.
- **בסשנים של ניר, Claude ממזג לבד** כשהבדיקות ירוקות (CLAUDE.md, כלל 9). במחשב של ניר מוגדר `FH_SELF_MERGE=1`, ולכן השומר (`tools/hooks/guard.js`) לא עוצר מיזוג. אצל אוראל השומר עוצר לאישור, עד שאוראל יחליט אחרת. אם הוא רוצה כמו ניר: `"env": {"FH_SELF_MERGE": "1"}` בהגדרות של Claude במחשב שלו (`~/.claude/settings.json`).
- **כל מיזוג עם סיכום:** `gh pr merge <n> --squash --subject "..." --body "מה נעשה: ... למה: ... מי אישר: ..."`. בלי `--body` השומר חוסם.
- **PR שמחכה הרבה זמן מתנגש שוב ושוב.** אם יש PR עם בדיקות ארוכות (תלת-ממד), עדיף לעצור את המיזוגים האחרים עד שהוא נכנס.
